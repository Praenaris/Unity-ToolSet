# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Praenaris ToolSet** (`com.praenaris.toolset`, published on OpenUPM): a Unity 6 package of larger, opt-in runtime subsystems with their Project Settings pages, built on top of **Praenaris DevKit** (`com.praenaris.devkit`). It is a generic, publicly distributed package: nothing in it (code, comments, docs, this file) may reference or depend on any specific project that uses it.

For development the repo is usually cloned as an **embedded package** into some Unity project's `Packages/` folder (often next to an embedded DevKit clone), so edits compile in that project's open Editor immediately.

Dependencies (`package.json`): DevKit, `dev.tabernero.simplejson` (namespace `Tabernero.SimpleJSON`), `com.cysharp.unitask`; **Steamworks.NET is optional**. The `com.praenaris.devkit` pin in `package.json` is kept at the latest released DevKit on every version bump (see Git and releases); when ToolSet starts using a DevKit API that isn't published yet, it can only move once the DevKit release that ships it is tagged.

## Assembly layout

There is **one asmdef**, `Praenaris.ToolSet.asmdef` (`rootNamespace: Praenaris`, `autoReferenced`), at the repo root. There is **no Editor asmdef**: everything under `Editor/` compiles into the same runtime assembly, so **every Editor file is wrapped whole in `#if UNITY_EDITOR` … `#endif`** (before the usings, after the namespace). New editor code must do the same, or player builds break.

`versionDefines` in the asmdef turn installed packages into defines: `SIMPLEJSON`, `UNITASK`, and `STEAMWORKS_INTEGRATION` (only when `com.rlabrecque.steamworks.net` is installed). Steamworks calls are always behind `#if (STEAMWORKS_INTEGRATION && !DISABLESTEAMWORKS)`, and the code must compile without it. The asmdef also references `Unity.InputSystem`; Input System code goes behind Unity's own `ENABLE_INPUT_SYSTEM`, so it compiles out when the project's active input handling doesn't include it.

```
Runtime/
├── ASubsystem.cs          base of the static subsystems
├── Cursorman/             cursor presets by ID, auto-hide, [Cursor] ID dropdown
├── Fileman/               async local file read/write + UnityWebRequest fetch (Praenaris.Tools)
├── Savedata/              JSON savedata in slots and resources (+ Legacy/)
├── Situations/            situations subsystem (scaffold)
├── Localizer/             string tables from local resources / streaming assets / online sheets
├── Prefabricator/         spawns prefabs from settings on game start
├── Sounder/               pooled AudioSource player (+ Animator/ state hooks)
├── UniBuilder/            build tool subsystem (in development)
└── Integration/           platform façade: Achievements, RichPresence, Steamworks/SteamManager
Editor/
├── Building/              Subsystems/ menu togglers (one per subsystem) + Steamworks disabler
├── Drawers/               property drawers / custom editors for the subsystem data
├── Settings/              Project Settings providers under Project/Praenaris/…
├── Sounder/               AudioSourceConfig drawer, SounderCue inspector, EditorSounderPreview
└── Toolbars/              Unity 6.3 main toolbar elements (MainToolbarElement): time scale slider + reset and Localizer language dropdown (Play Mode only, the dropdown needs `ENABLE_LOCALIZER`), Project Settings button
Resources/[SteamManager].prefab
```

## Subsystem defines

Every subsystem is compiled out unless its define is on: `ENABLE_SAVEDATA`, `ENABLE_LOCALIZER`, `ENABLE_PREFABRICATOR`, `ENABLE_SOUNDER`, `ENABLE_INTEGRATION`, `ENABLE_CURSORMAN`, `ENABLE_SITUATIONS`, `ENABLE_UNIBUILDER`. **Each file of a subsystem is wrapped whole in its define.**

- The togglers in `Editor/Building/*SystemToggler.cs` are `[InitializeOnLoad]`: their static constructor registers the define in its *off* form (`_ENABLE_X`, leading underscore = off) through DevKit's `BuildDefines.SetDefinition` if the project has neither form yet, and their `Subsystems/<Name> [ON|OFF]` menu item flips it. A new subsystem gets its own toggler copied from these.
- `DisableSteamworksToggler` flips `DISABLESTEAMWORKS` (Steamworks.NET's own switch) from the `Integration/Steamworks` menu.
- Settings providers must compile **in both states**: under `#if ENABLE_X` they derive from `AScriptableSettingsProvider<XSettings>`, otherwise from the non-generic `AScriptableSettingsProvider`, and they show an "Enabled" toggle that calls `BuildDefines.SetDefinitionState` (see `SavedataSettingsProvider`).

## How a subsystem is built

- **Static class + settings asset.** `ASubsystem<TSelf, TSettings>` (`Runtime/ASubsystem.cs`, namespace `Praenaris`) holds the static `_settings` and a `_starting` `TaskCompletionSource`. The subsystem marks itself `[Preserve]`, hooks a `[RuntimeInitializeOnLoadMethod]` that calls `Startup(onStarting, onStarted)`, and public entry points `await _starting.Task` before touching state. `Startup` awaits `SingletonScriptableObject<TSettings>.GetInstanceAsync()`.
- **Settings are a DevKit `SingletonScriptableObject<T>`** (`[CreateAssetMenu(menuName = "Praenaris/Settings/<Name>")]`, public fields). Its instance is only set in the asset's `Awake`/`OnValidate`, and `GetInstanceAsync` polls every frame until then, so **the asset must be loaded at startup**: `AScriptableSettingsProvider<TSettings>` finds the first asset of that type (or creates `Assets/<TypeName>.asset`) and adds it to **Preloaded Assets** via DevKit's `PreloadedAssets`. If the settings page was never opened, a subsystem can wait forever.
- `ASubsystem.Settings` (and e.g. `Savedata.Data`) have an `internal` setter so the settings editors can drive the subsystem from Edit Mode.
- **Settings pages** derive from `AScriptableSettingsProvider<TSettings>` at `Project/Praenaris/<Name>` (Integration modules nest under `Project/Praenaris/Integration/<Module>` through `AIntegrationModuleSettingsProvider`). It draws every visible property; override `OnPropertyGUI` (return `true` if you drew it), `OnBeforeGUI`, `OnAfterGUI`. `Project/Praenaris` itself is `PraenarisEditorSettingsProvider` (banner, links), backed by a `ScriptableSingleton` in `ProjectSettings/PraenarisSettings.asset`.
- **Async**: **avoid UniTask in the package as much as possible** (it's fine in consuming projects, not convenient here); new and reworked code uses `System.Threading.Tasks` (and Unity's `Awaitable` where a frame/main-thread wait is needed). `ASubsystem`, Savedata, Fileman and Localizer already do. UniTask remains only in older code: Sounder (`Sounder`, `SounderPool`), and Savedata Legacy; don't spread it, and move code off it when reworking it.

## Subsystems

**Savedata** (`Praenaris.Savedata`, the reworked one): one in-memory `JSONNode` (`Savedata.Data`) split across **resources** (`SavedataResource`: root folder enum `SavedataRootPath` (in Fileman), optional company/product subfolders, relative path, `Slotted` adds `_<slot>` to the file name, `Keys`; `GetFullPath(slot)` resolves it through `Fileman.ResolvePath`, so it's a full file path or a `<PlayerPrefs>/...` key). `SavedataSettings.Resources` is the `FallbackResource` followed by the `ResourceOverrides`. On load all files are read in parallel and merged, later resources winning; on save each top-level key goes to the **last** resource listing it, unlisted keys go to the fallback. The settings' `SavedataVersion` is stamped under `SavedataVersionKey` on save, and `OnLoaded` reports `SavedataLoadState` (`FreshNew` / `OlderVersion` / `LatestVersion`); migrating older versions is up to the consuming code. The current slot persists in PlayerPrefs (`SAVEDATA_CURRENTSLOT`); `LoadOnGameStart` loads it at `AfterAssembliesLoaded`. Load/Save are serialized by a semaphore and clear `IsReady` while running. Accessors live in `Savedata.GettersSetters.cs`: `Get*`/`TryGet*` with fallbacks, `Set*` aliases of `TrySet*`, which **return `false` and drop the value while `IsReady` is false**; whole objects go through `ISavableNode` (`JSONNode`) or `ISavableString`. The settings page has a slot browser that loads, edits and saves the raw JSON.

Known Savedata issues, to be fixed (most serious first; remove each one from this list once it's fixed):

1. **First save can fail**: `Fileman.WriteToFile` doesn't create the target folder (Legacy did), so saving into a missing `AppData/<Company>/<Product>/` throws `DirectoryNotFoundException`, which is only logged, and nothing is written.
2. **Non-atomic writes, corruption becomes data loss**: files are overwritten in place (no temp file + replace, no backup). A corrupt or non-object file loads as `null`; if no version key is found in any resource the load reports `FreshNew` with empty data, and the next save overwrites the corrupt file. A corrupt override file silently loses its keys the same way.
3. **Values set during Load/Save are dropped**: `Set*` return `false` while `IsReady` is false, so frequent saves lose concurrent writes. Saving a snapshot of `Data` instead would let setters keep working.
4. **`IsReady` can stay false**: it's only restored on success (not in a `finally`), and `Save()` before any `Load()` (with `LoadOnGameStart` off) throws a `NullReferenceException` on the null `_data`.
5. **No startup wait**: `Load`/`Save` have `await _starting.Task` commented out, so an early call throws on a null `_settings`.
6. **No per-platform roots**: a resource has one `SavedataRootPath` for every platform, so it can't be `AppData` on desktop and `PersistentData` on WebGL (where the special folders don't persist). Fileman's forced PlayerPrefs (see Fileman) covers the platforms listed there, but there's no per-platform choice between file roots.
7. **Storage is limited to files and PlayerPrefs** through Fileman: no backend seam for WebGL IndexedDB sync (`syncfs`), console save data APIs or tests. SimpleJSON is the only format.
8. **No loaded `Task`**: consumers can only poll `IsReady` or hook `OnLoaded` (which misses a load that already happened); there is nothing to `await` like Legacy's `Loading`.
9. **No change notifications per key**: nothing like Legacy's `Subscribe`/`SubscribeAndReload`.
10. **Smaller ones**: `OnLoaded`/`OnSaved` are public `Action` fields, not `event`s; `OnLoaded` runs while the load still holds the semaphore, so a handler awaiting `Save()` waits for the load to end; `Load(slot)` switches the current slot even if loading fails; `Slotted`/`MaxSlots` aren't enforced at runtime; no per-version migration hook; key routing is top-level keys only; everything is static (hard to test).

**Savedata Legacy** (`Praenaris.SavedataLegacy`, `Runtime/Savedata/Legacy/`, `ISavableData` + wrappers, `SavedataLegacySettings` and its own settings page): the previous API, kept compiling under the same `ENABLE_SAVEDATA` for projects still on it. Its reads and writes go through Fileman, so `ForcePlayerPrefs` applies to it too, with the same `<PlayerPrefs>/Company/Product/<file>` keys the new Savedata uses (`GetStoragePath`); otherwise its paths are unchanged (`GetOptimizedPersistentDataPath`). Fix it if it breaks, don't extend it.

**Fileman** (`Praenaris.Tools`, always compiled): `Exists` / `Delete` / `ReadFromStorage` / `WriteToStorage` (UTF-8 default, `null` when missing), `FetchWebResource` / `FetchToFile`, plus Editor-only `TextAsset` variants (`ReadFromAsset` / `WriteToAsset` / `FetchToEditorAsset`).

- **Roots**: `SavedataRootPath` (`AppData`, `PersistentData`, …, `PlayerPrefs`; append new entries at the end, assets store the number) and its `Resolve()` extension live here. The local methods have overloads taking `(SavedataRootPath root, string relativePath)`, which resolve it with `ResolvePath` and call the raw path version.
- **PlayerPrefs storage**: a path starting with `PlayerPrefsRoot` (`<PlayerPrefs>/Company/Product/file.json`, separators normalized to `/`) is a PlayerPrefs key holding the content as a string (the encoding is ignored); the raw methods pick PlayerPrefs or `System.IO` from that prefix (`IsPlayerPrefsPath`), so Editor asset paths and plain paths always stay files. Each write and delete calls `PlayerPrefs.Save()`. PlayerPrefs only work on the main thread, so never `ConfigureAwait(false)` on the way to them.
- **Forced PlayerPrefs**: `ForcePlayerPrefs` is true with the `FILEMAN_FORCE_PLAYERPREFS` scripting define, which the top of `Fileman.cs` also `#define`s on the platforms it lists (`UNITY_SWITCH` so far; add more to that `#if` with `||`). That `#define` only applies inside `Fileman.cs`, so other code must read `Fileman.ForcePlayerPrefs`, never `#if FILEMAN_FORCE_PLAYERPREFS`. When forced, `ResolvePath` maps every root to a PlayerPrefs key. It also applies in the Editor while that platform is the active target.
- **Later, not now**: replace the `PlayerPrefs.Save()` on every write with a `Fileman.Flush()` (or a commit step) that Savedata calls once after writing all its resources, so a save doesn't flush PlayerPrefs once per resource on the main thread; the same hook would fit platforms whose storage needs a commit.

**Prefabricator** (`DragonResonance.Prefabricator`): at `AfterSceneLoad` instantiates each `SPrefabricable` (`Prefab`, `Amount`, `Persistent` → `DontDestroyOnLoad`), named after the prefab. Await `Prefabricator.SpawningTask` to know they exist.

**Sounder** (`DragonResonance.Sounder`): `Sounder.Play` / `PlayAndAwait` / `PlayAndGet` take an `AudioSourceConfig` (an `AudioResource` + mixer group) and use a pooled `AudioSource` from `SounderPool`, a DevKit `PersistentSingletonPossumBehaviour` that releases sources when they finish; `AnimatorStateSounderPlayer` plays configs from Animator states. `SounderCue` is a ScriptableObject holding one config (`GetConfig()`, `Play()`); its inspector's Play / Restart / Stop go through `EditorSounderPreview`, which plays on a pooled source in Play Mode when a `SounderPool` exists, and otherwise on a temporary hidden `AudioSource` (so it works in Edit Mode, through the mixer). Sounder predates `ASubsystem` and still has its own UniTask startup.

**Localizer** (`DragonResonance.Localizer`, static `Localizer`; under an overhaul, this is the intended design): string tables live in a DevKit `HeaderedSheet<string>` (keys as rows, columns headed by plain strings, mostly languages), filled by joining (DevKit `HeaderedSheet.JoinTSV`: columns matched by heading, missing ones added) every source of `LocalizerSettings.LocalizationDataSources` (`LocalizationDataSource`: `Type` `TextAsset` / `StreamingAsset`, the asset or streaming path, an optional `Url`; `Path` is `null` for text assets outside the Editor, `Content` reads either kind) and sanitized by `BlacklistFilters`.

- **Startup**: first (try to) load every source already in the project, pick the language (the first of system language + `LanguageFallbacks` present in the sheet, unless `ChangeLanguage` already set one while starting), then refresh.
- **Online update (Editor only)**: after startup, in the background, download the latest version of every source with a `Url` **in parallel** and overwrite its file, with a timeout (`DownloadTimeout`, 15 s by default, `[Range(1, 60)]` in the settings). Once finished, reload all the data and refresh again.
- **Failures never stop it**: a source that fails to load, download or parse is logged, and the Localizer carries on with whatever data it could get.
- **Refreshing**: every refresh (language change, data loaded, data updated) invokes `OnLanguageChange`. Localizable components (`ALocalizable` → `LocalizableText`, `LocalizableEvent` → `BuildLocalizableEndpoint`, which can use another template in the Editor, `DEVELOPMENT_BUILD` or `DEMO_BUILD`) subscribe by default (`OnEnable`/`OnDisable`) through `Subscribe`/`Unsubscribe`, so they all refresh with it; `Subscribe` localizes the new one immediately once started, and nothing runs against the data before startup finishes.
- **Localizing** is instant: `Localize(template)` replaces `{Key}`, joining `Key:1`, `Key:2`… lines for composite keys, and `Localize(template, handler)` passes the result on. The old awaiting UniTask API (`LocalizeLegacy`, `ChangeLanguageLegacy`) was removed. Localizables auto-wrap a bare single-key template in braces on `OnValidate`, and override `LocalizationTemplate` to build the template at runtime. Their template field is `[LocalizationKey]`: a DevKit `AComboBoxAttributeDrawer` listing the keys (as `{KEY}`, composite `KEY:n` parts merged, grouped by the prefix before `_`) from the sheet column whose heading is `LocalizerSettings.KeysHeading` (`"Key"`); it loads the data once per domain in Edit Mode.
- **Columns are just strings, not only languages**: a column heading is a plain string, and not every column has to be a language, so the Localizer must also localize into any literal column. `Localize(template, string columnName)` (and its handler overload) reads the column with that heading; the `SystemLanguage` overloads only forward `language.ToString()`. Localizables read `CurrentLanguage` unless their override is ticked; then they read `_overridingColumn`, a string drawn by `[LocalizationColumn]` (a combo box of the sheet's headings, the keys column left out; it loads the data the same way `[LocalizationKey]` does). `CurrentLanguage`, `ChangeLanguage` and `AvailableLanguages` still deal with real languages only (headings that parse as `SystemLanguage`), and so does the toolbar's language dropdown. Keep new API string-based underneath, with `SystemLanguage` as a convenience on top.
- **Localized assets** (`ALocalizableAssetEvent<TAsset>`, one five-line concrete class per type: `LocalizableSpriteEvent`, `LocalizableAudioClipEvent`): a sibling of `LocalizableEvent` whose localized text is an asset path inside any `Resources/` folder, without extension; it loads it (`Resources.LoadAsync` in Play Mode, `Resources.Load` in Edit Mode) and invokes `UnityEvent<TAsset> Target`, wired in the Inspector to a dynamic setter such as `Image.sprite` or `AudioSource.clip`. Only the latest request invokes, so a slow load never overwrites a newer language; a missing asset logs an error and keeps the previous one. A new type is just another empty subclass in its own file.
- **Settings page**: just under the normal settings, a table preview of the final data (the merged and filtered sheet). Ctrl+C or right-click › Copy copies the selected rows' keys (from the `KeysHeading` column, composite parts merged, one per line, bare without braces).

**Cursorman** (`Praenaris.Cursorman`): cursor presets switched by string ID. `CursormanSettings` has the general configuration on top (`CursorMode`, `DefaultCursor` preset ID, empty for the system cursor, and the `PointerInput` `InputActionReference`, Input System only) and the `Presets` list below; each `CursorPreset` (`[Serializable]` class, one-line `CursorPresetDrawer`) has an `Id`, a `Sprite` (its hotspot comes from the sprite's pivot) and `AutoHide` + `AutoHideDelay` seconds. `Cursorman.Set(id)` is the entry point: it awaits the startup, looks the preset up in the settings the first time and caches it in a dictionary by ID (with an uncompressed RGBA32 copy of the sprite's rect, so the sprite's texture needs Read/Write), logs an error and keeps the current cursor on an unknown ID, and on `null`/empty resets to `DefaultCursor` (`Reset()` is the same). The default is applied in `onStarting`, so `Set()` calls waiting on the startup land after it. An auto-hiding preset runs a UniTask loop that hides the cursor after the delay without `PointerInput` performing and shows it on movement; switching preset stops it and restores the visibility it took; without `PointerInput` it only warns and never hides. `[Cursor]` (`CursorAttribute` + `Editor/Drawers/CursorAttributeDrawer.cs`) draws a string as a dropdown of the preset IDs ("None" = empty), keeping an unknown ID visible as "(Missing)". DevKit has an unrelated `Praenaris.GUI.Cursorman` MonoBehaviour; they only clash if a file imports both namespaces.

**Situations** (`Praenaris.Situations`): scaffold only so far: an empty `ASubsystem` (`Startup()` at `AfterAssembliesLoaded`), an empty settings asset, its settings page and toggler. Grow it following the pattern above.

**UniBuilder** (`Praenaris.UniBuilder`, `Runtime/UniBuilder/`; always capitalized **UniBuilder**, never `Unibuilder`): a larger tool under active development, starting from the same scaffold (`UniBuilder` subsystem, `UniBuilderSettings`, `Project/Praenaris/UniBuilder` page, `Subsystems/UniBuilder` toggler). Keep this entry updated as its design settles.

**Integration** (`Praenaris.Integration`): `IntegrationSettings`, plus modules with their own settings and pages. **Achievements**: `AchievementsSettings.Achievements` is a list of `Achievement` structs (name, Steam achievement/stat IDs, optional progression stat range, icons); the custom editor (`Editor/Drawers/AchievementsSettingsEditor.cs`) keeps one `AchievementReference` sub-asset per entry inside the settings asset, matched by the `[ReadOnly] ChannelGuid` it generates, so game objects can reference a single achievement and call `Progress` / `Achieve` / `Unachieve`. Steam rejects stat values outside the stat's range, hence the clamping in `Achievement.Progress`. **RichPresence**: settings page only so far. `Integration/Steamworks/SteamManager.cs` is the community Steamworks.NET `SteamManager` (global namespace, its own style; leave it as is), spawned from `Resources/[SteamManager].prefab`.

## Code style

The DevKit/ToolSet source *is* the maintainer's house style; read a file of the same subsystem end-to-end before adding one. In short:

- `.editorconfig`: tabs, LF, UTF-8, **no trailing newline**.
- Allman braces for namespaces, types and methods; K&R for control flow, with `else` on its own line after `}`. Single-statement bodies drop braces onto the next indented line; guard clauses stay inline (`if (_pool != null) return;`).
- `#region` order **Constructors → Events → Publics → Inheritables → Privates → Properties**, contents indented one extra level; split with suffixes (`#region Publics - Setters`). Two blank lines between usings and the namespace, around regions and between member groups.
- `using` ordinal-alphabetical with children before their parent (`System.Threading.Tasks;` then `System.Threading;` then `System;`). Usings only needed under a subsystem define go in a separate `#if` block after the others.
- Private fields `_camelCase`, always explicitly initialized; settings assets use public PascalCase fields. Lazy caches `_x_internal` with a `// Caching only, use the property instead` comment, and **`[NonSerialized]` when they live on a ScriptableObject or EditorWindow**. Read own properties through `this.`. Explicit types, no `var`. Prefixes `A` abstract, `I` interface; **structs take no prefix**, serializable or not (`AudioSourceConfig`), and older `S`-prefixed ones (`SPrefabricable`) are legacy, renamed only when asked (it's a breaking change). Expression bodies where they fit. Inline comments after a tab.
- Use the DevKit primitives: `Log.Info/Emphasis/Warning/Error/Exception` (`DragonResonance.Logging`, conditional on `ENABLE_LOGGING`) instead of `Debug.Log`, the DevKit extensions (`IsNegative()`, `IsZero()`, `Clamp`…) and attributes (`ShowIf`, `ReadOnly`, `SpritePreview`). Something generic that ToolSet needs belongs in **DevKit**, not here.
- **Dependencies always sorted alphabetically**, wherever they are listed: `dependencies` in `package.json`, `references` in the asmdef, `using` directives (with the children-before-parent rule above). Keep the order when adding one.
- **Copyright footer on every code file**: every `.cs` ends, two blank lines after the last `#endif`/`}`, with the Praenaris ASCII-art Apache footer (11 lines, `Licensed under the Apache License, Version 2.0` … `Copyright © 2026`) and **no newline after it**. New files get it too. Copy it from an existing file, never retype it, and never use any other copyright notice here.
- **Namespaces are mid-rename**: older code is `DragonResonance.*` (Localizer, Prefabricator, Sounder, `DragonResonance.Editor.*`), newer code `Praenaris.*` (`ASubsystem`, Savedata, Integration, Fileman). Match the file or subsystem you're in, and don't rename one file's namespace in isolation; new subsystems use `Praenaris.<Name>`.
- Every asset/folder needs its `.meta` (Unity generates them when the Editor of the project embedding the package refocuses; commit them).

## Compile-checking

There is no CLI build. Check edits with Roslyn from the Unity install (`<Editor>/Data/DotNetSdkRoslyn/csc.dll` under `dotnet`), feeding it the embedding project's generated `Praenaris.ToolSet.csproj`: its `<HintPath>`s, its `<DefineConstants>`, every `<Compile Include>`, `-langversion:9.0 -noconfig -nostdlib+ -target:library`, and `Library/ScriptAssemblies/Praenaris.DevKit.dll` (a fresh build of it if DevKit changed too) for the `<ProjectReference>`. Pass `-noconfig` on the command line, not in the rsp. `-nowarn:CS0436,CS0169,CS0414,CS0649,CS0108,CS0219,CS0162,CS0067,CS1998,CS4014` keeps the log readable.

- The csproj defines are **the embedding project's**: a subsystem that project has switched off (`_ENABLE_SOUNDER` etc.) is not compiled at all. When editing such a subsystem, add its `ENABLE_*` define to the rsp by hand, and when touching shared code (`ASubsystem`, settings providers, drawers) check with the defines both on and off.
- `STEAMWORKS_INTEGRATION` code can only be checked in a project with Steamworks.NET installed; say so when it's left unverified.
- Files added outside the Editor aren't in the csproj yet: append them to the rsp.

## Git and releases

- Branches: work on **`develop`** (or `feature/<name>` merged into `develop` with `--no-ff`). `master` is only written by the release workflow.
- **Local sessions** (working on the maintainer's machine): **never touch git** unless explicitly asked: no staging, committing, merging, branching, stashing, resetting, pulling or pushing. Read-only commands (`status`, `diff`, `log`) are fine; leave every change in the working tree for the maintainer to handle.
- **Cloud sessions** (Claude Code on the web / remote): at the **start of every cloud session**, merge the development branch (`develop`) into the session's branch to stay up to date. After that, **stay on the session's own branch** unless told otherwise: work, commit and push freely there, but don't check out, create, merge into, push to, open PRs against or otherwise manage any other branch unless explicitly asked.
- Commit messages: one imperative, capitalized line, no period, usually no body ("Fix status check for achievements", "Add refresh button to the Savedata settings provider").
- **Bumping `version` in `package.json` and pushing is a release.** `.github/workflows/auto-merge-and-tag.yml` runs on every push: if no `v<version>` tag exists, it merges the pushed branch into `master` and tags it; the tag triggers `auto-sign.yml`, which signs the package with the UPM CLI and creates the GitHub Release, and OpenUPM picks the tag up. Outside a cloud session's own branch, never push without being asked.
- **Every set of changes bumps `package.json` `version`**, as part of the change itself and **without committing** (the maintainer commits; the bump goes into that same commit):
  - **Patch** (`1.4.2 → 1.4.3`): backwards compatible: bugfixes and a few small additions.
  - **Minor** (`1.4.3 → 1.5.0`, patch reset to 0): bigger features (e.g. a new subsystem or module) or any breaking change (renamed/moved/removed public members, namespace moves, changed signatures, settings or savedata formats consumers rely on).
  - **Major**: never; only the maintainer bumps it.
  - One bump per set of changes, not per edit. Compare `package.json` with the committed one (`git diff -- package.json`) and the latest tag (`git tag --sort=-v:refname | head -1`): if the working tree already carries an uncommitted bump, the new changes share it, only raised from patch to minor if they need it. If the version is ahead of the latest tag because of an unpushed commit, ask whether to bump again.
  - **Every bump also moves the `com.praenaris.devkit` dependency to the latest released DevKit**, so ToolSet always ships against the newest DevKit. "Released" means a `v<version>` tag exists on the DevKit remote: check with `git ls-remote --tags https://github.com/Praenaris/Unity-DevKit.git` (a local DevKit clone's tags or `package.json` can be behind or ahead of it). Never pin a DevKit version that isn't tagged yet, or consumers can't resolve the package; if the change needs an unreleased DevKit API, leave the pin at the latest release and say in the summary that it has to move once that DevKit version is out. Mention the pin change (or that it was already current) in the summary.
  - Say which bump you made and why in the summary.
  - **Cloud sessions: don't bump unless asked.** Pushing the session's branch with a new, untagged version would merge it into `master` and publish a release; leave the bump for when the work lands on `develop`, and mention it's pending in the summary.
- Everything in the repo root ships in the package, so keep non-package files out of it (or make sure they're intended to ship).
